## Expansion and interpretation

The [implementation contracts](authentication-test-lab-contracts.md) define explicit catalog rows/IDs, exact profile membership, independent fixture inputs/results and protocol controls; [terms with examples](authentication-test-lab-terms.md) explain the language. Store expanded rows explicitly and validate complete finite domains, without a formula language. Physical production bindings still require the fresh P2 audit.

This matrix turns the earlier [coverage inventory](authentication-test-lab/coverage_candidates.md) into finite execution definitions. Each named variant gets the requirement ID `<group>.<variant>`. Axis rows expand the explicitly stated Cartesian product and put each axis value in the requirement ID. A callable binding supplies the actual execution ID; one audited execution may satisfy several requirement rows. Required capability is evaluated per variant, not by blocking an entire group when a baseline variant is independently runnable. Profiles select and deduplicate these IDs; they do not multiply them by every layer.

There are **41 groups and 980 requirement/assessment entries** for the initial Windows artifact: **912 active automated requirements (389 extension behavior and 523 custom test-application checks), 24 host-specific manual entries, 16 manual capability assessments and 28 excluded historical entries**. All active automated requirements have bindings, sharing 851 executions; a binding is not a passing result. The full fixture matrix remains useful: it prevents a faulty verification service from accepting incorrect credentials and producing false extension passes. Existing lower-layer tests may own several entries through one execution. See the [relevance review](authentication-test-lab/relevance-audit.md) for the retained, reused and excluded checks. The group table below preserves historical ID counts; excluded rows remain visible and do not run or earn passes.

Variant strings are data labels, not new production settings. The adapter renders native references/output selectors from the approved production contract. Cases that require an absent contract stay blocked. In particular, the tag matrix's 48 ordinary representable cases do not select new multi-output syntax. CORE.recovery's 80 cases are policy assertions with controlled runner/transport boundaries; RUN.recovery and H03 establish distinct real-browser and real-host facts.

The [existing-test ledger](authentication-test-lab/existing_test_audit.md) is preliminary because `java-playwright` is still being developed. Before implementing/scheduling production entries at P2, rerun the complete audit against the actual integrated revision and replace these provisional bindings with current assertion/input witnesses. Extend only verified gaps; do not duplicate an existing owner. A stale/source-only match is not a passing result. The requirement domain is separate from the eventual number of reused/new executions.

## User-visible diagnostic contract

These 18 requirements concern what the user is actually told. Use independently controlled outcomes as the expectation; copying the returned production error category into an expected string cannot establish accuracy. Exercise existing production mapping/formatting/state code and inspect the actual output it supplies to the user. A specific detail cannot excuse a contradictory headline or status. Required/forbidden meaning is checked with semantic assertions; the examples below do not freeze punctuation or complete strings.

| Variant | Controlled condition | Required displayed meaning and prohibited confusion |
| --- | --- | --- |
| `connection-refused` | The selected destination refuses the connection. | Identify connection establishment failure at the affected stage; do not invent a missing cookie or rejected password. |
| `tls-untrusted` | Strict certificate validation rejects the fixture certificate. | Identify TLS trust/certificate validation; do not call it missing authentication output or suggest disabling trust checks. |
| `navigation-timeout` | The navigation exceeds its declared deadline without a more specific confirmed cause. | Identify the timed-out stage and uncertainty; do not assert bad credentials or a connection refusal. |
| `step-target-missing` | A required element/action target is absent after successful page delivery. | Identify the failed journey step/target or its wait deadline; do not claim the page connection failed. |
| `login-rejected` | The controlled application explicitly confirms login rejection. | Identify the confirmed rejection; avoid guessing password failure when the fixture supplied no such evidence. |
| `missing-cookie` | The response/journey completes but the selected cookie is absent. | Identify extraction failure and the safe selected cookie/output name. For example, “Expected cookie session was not found”; “Connection failed” must not appear as the cause. |
| `ambiguous-cookie` | Multiple applicable cookies match the configured selector. | Identify ambiguous selection; do not report no matching cookie or a network failure. |
| `missing-response-token` | A valid received response lacks the selected token field or match. | Identify the missing selected response output; do not report a connection failure or malformed response. |
| `invalid-response-format` | The received extraction input is malformed for the configured parser. | Identify parsing/format failure at extraction; distinguish it from a well-formed response missing a field. |
| `incomplete-output-set` | One required output is absent while another is obtained. | Identify the incomplete required set and missing role; do not publish overall authentication success from the partial set. |
| `protected-use-rejected` | Obtained credentials are submitted and the protected service rejects them. | Identify observed protected-use rejection; preserve that acquisition/extraction completed and do not invent its root cause. |
| `unresolved-tag` | A declared tag refers to an unavailable journey/output. | Identify the unresolved reference and affected request/journey safely; preserve the atomic-stop outcome rather than report a network request failure. |
| `unsupported-capability` | A selected required capability is unavailable. | Identify the missing prerequisite or unsupported capability and blocked outcome; do not suggest that a connection/login attempt failed if none ran. |
| `cancelled` | The user cancels an active attempt. | Identify cancellation, with no invented connection or credential error and no stale success for the cancelled attempt. |
| `attempts-exhausted` | Three permitted temporary-network attempts fail within one recovery episode. | Show the three-attempt count, paused state and known underlying failure/stage. The recovery wrapper must not replace it with an unrelated generic diagnosis or offer an automatic fourth attempt. |
| `stale-result` | A retired attempt/revision completes after a newer result or another journey changes. | Preserve the current journey/revision's displayed result. Historical failure remains attributed to its old attempt; it cannot overwrite another journey or the newer result. |
| `extraction-only-success` | Extraction completes and protected use has not been verified. | Identify extraction success with protected access unverified; do not claim that the application accepted the credentials. |
| `success-after-failure` | A current attempt succeeds after a previously recorded failure. | Show current success at the actually established evidence level; clear stale active error presentation, preserve historical records, and follow the production pause/rearm contract. |

Every variant also checks safe journey/output attribution, current saved revision/attempt, compatible summary/details/status and applicable request feedback, and omission of raw credentials or sensitive URLs. Feedback must match the caller's actual outcome: ordinary unchanged forwarding with a warning differs from atomic stopping of an unresolved tagged request. A paused journey must not be described as blocking all unrelated traffic. Assert the production's known stage/cause or explicit uncertainty; the lab does not invent production error codes, infer a password failure from a generic page, or add a replacement classifier/renderer. If the production cannot expose the relevant result/presentation, the requirement is blocked pending its contract.

Reuse DiagnosticsTest/editor assertions after the full P2 audit. Each CORE.diagnostics requirement has one component owner; separate BROW/TLS requirements own real failure propagation. For example, deleted-mid-flow owns the actual missing-cookie cause and unreachable-hop owns the actual connection-failure cause. These are separate requirements, not supporting dependencies of a component row. Existing negative production cases check their relevant diagnostic facts in the same owning execution, including missing setup/secrets and PIN rejection or unknown outcomes; these 18 representatives do not exempt other messages from coherence requirements. Component checks own the semantic matrix. H02/H05 establish actual-host feedback wiring; the existing H05 test/paused-test checkpoints include contrasting missing-cookie and connection-failure observations, and late-result establishes freshness. These are additional observations within the existing six H05 entries, not 18 new Burp scenarios or a second full browser matrix. One execution may satisfy several diagnostic and pre-existing requirements when it records the corresponding assertions.

## Required interactions and observation boundaries

* FIX.extra and browser cases use the contract companion's explicit assignments, statuses, identities, hops and cookie attributes. Strict subsets retain 511/42/469 accounting; the separate legacy-cookie route permits different issuances for the same account only.
* Real OAuth/SAML journeys exercise the extension and prove its captured outputs at the accepting services. Signed-message and provider protocol-validator suites are excluded; they do not establish extension correctness.

* Configured upstream proxy authentication is outside the lab scope, including support, bad-credential/challenge handling and rejection/configuration tests. Do not replace the removed cases with negative tests. The mTLS proxy's internal per-attempt credentials are a separate retained requirement; application HTTP Basic/Digest capability assessments are also separate from upstream proxy authentication.
* Assign the browser-visible OIDC client, backend-only OIDC client and SAML client different saved journeys. Every combined automatic case still gets its outputs from one journey. Explicit multi-identity tag slots are checked through production parsing/selection; they are not inputs to combined automatic authentication.
* FED.broker.combined-outputs is the targeted federation/redirect/multiple-output interaction. CORE.lifetime.late-old-401 and CORE.outputs.late-retired-attempt cover version ownership. RUN.recovery supplies actual browser evidence; H04 owns actual proxy-interception recursion.
* Every successful credential-use case verifies the expected identity at its accepting service. Extraction-only diagnostic cases explicitly report that protected access remains unverified. Browser-only fixture validation cannot substitute for invoking the production runner. Provider/client negative controls validate their target and are labelled accordingly.
* `FED.negative.code-expired` supplies an immediate simulated backend rejection to test extension feedback, with no expiry wait. All former signed-message consumer-validator controls are excluded.
* CORE.resources unload/backoff tests and RUN.recovery.cancel-cleanup retire pending work before completion. Paused-state cases also observe continuing demand while the coordinator is still alive; shutting it down first cannot prove that pause prevented a storm.
* H02 checks a case-owned sentinel with a positive control. Any decrypted application bytes fail the non-delivery assertion, including malformed requests. TLS preconnection/handshake observations remain separate.
* CAP.assessment entries are deliberately unpromised. Supply operator recipes and capability conclusions rather than invent production challenge solving, integrated-authentication support or protocol grant engines. TOTP/delayed-approval can be promoted to automated cases only when a reviewed journey/control contract establishes them. Physical-token verification is additional manual evidence under TLS.mtls and CORE.retry; SoftHSM does not satisfy it.

## Runtime accounting

The implementation emits one expanded row per execution, with estimated startup/case/teardown time and later observed duration. Group setup is counted once per owned environment, not once per assertion. Serialize real-provider/session resets and browser cases by default; explicit concurrency cases control their own batch. There is no measured total runtime yet. The catalog must expose counts of runnable, blocked, manual, unsupported and unassessed entries, and a selected profile cannot turn missing evidence into a pass.

The A7 limit witnesses use the captured production limits: wrapper depth 8, distinct journey references 16, cumulative tagged text 1 MiB, matching JSON response 1 MiB, complete expanded request 4 MiB, and extraction regex source 4096 UTF-8 bytes. The byte dimensions are measured before the relevant decoder/parser or after complete request reconstruction, as applicable. `below` means limit minus one; `at` means the exact limit; `above` means limit plus one. The existing 256-tag node ceiling and 64 KiB normalized-token ceiling retain their focused owners in addition to this six-dimension catalog. Unmarked large uploads are outside the tagged-message ceiling. These mappings describe the audited implementation, not an increased supported limit.

The stable `CORE.diagnostics.step-target-missing` ID covers a target that the controlled scenario does not produce. The extension can establish that the action timed out; it cannot establish whether the cause was a wrong selector, a slow page or missing application state. Require a timed-out action message with the correct step, and reject an invented connection/password diagnosis. Its catalog revision therefore records `action-deadline` / `step-timed-out`, rather than claiming an unobserved root cause.
