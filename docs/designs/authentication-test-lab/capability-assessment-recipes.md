# Remaining capability assessments

2026-11-07. These are preparation recipes for the sixteen `CAP.assessment` entries, not executed tests or support declarations. All sixteen remain UNASSESSED in the catalog ledger. The production input is the integrated-main capture identified in the current audit (historical reference). A successful automated subset does not close these assessments.

For each assessment, retain the artifact/source identity, journey definition without secrets, prerequisite, actual completion or failure, safe account/session proof and owned-resource cleanup. Classify only the behavior observed: supported automatically, supported with an operator, unsupported for a stated operation, or still unresolved. Do not classify a whole authentication protocol from one page or from source inspection alone.

Use an explicit Test first. If it returns credentials, send them to the intended protected endpoint and verify the expected account and required credential combination. Observing an HTTP success or capturing an artifact alone is insufficient. Each later product attempt starts with a fresh context; a separate selected-cookie verifier must never seed a later production attempt.

| Assessment | Concrete check to prepare | Evidence still needed |
| --- | --- | --- |
| `totp` | A login asks for a changing one-time code after the password. Enter the current code in a visible attempt, then prove the resulting credentials. Run again after that code changes. | Separate one successful operator-assisted login from automatic generation of a new code. Native steps accept saved inputs; no code generator is established. A controlled code prompt and completion contract are needed. |
| `delayed-approval` | After submitting the password, hold the application's approval screen. Approve externally, then observe the journey continue to usable credentials. Separately cancel while waiting. | A controlled approval gate and reviewed wait budget. Do not introduce a real-time thirty-second sleep; release a gate or cancel promptly. Existing coordinator deadline/cleanup checks remain their lower-layer owners. |
| `webauthn` | A visible login requests a passkey/security-key action. Complete it with the intended device and prove the resulting application credentials. | An available authenticator, actual browser/device interaction and cleanup. Software-token TLS tests do not establish passkey support. |
| `captcha` | A visible login pauses for a human challenge; the operator completes it, and the journey resumes to usable credentials. | An authorized controlled challenge and an observed operator-assisted completion. Do not infer automatic challenge solving. |
| `basic` | An application sends an HTTP Basic challenge during login. Observe whether the product-owned browser can complete it using the available configuration/operator interaction. Prove the resulting protected access. | An application challenge fixture and actual browser behavior. This concerns application authentication, not an upstream proxy. Supplying a fixed Authorization string by hand does not prove challenge handling. |
| `digest` | Repeat the application-challenge assessment with HTTP Digest, using a fresh browser context and a protected-access proof. | A Digest application fixture and observed completion/failure. Do not retest the server's challenge algorithm or proxy authentication. |
| `kerberos` | Use an authorized integrated-authentication application and observe the fresh product-owned browser's account and credential outputs. | Suitable Windows/domain configuration and an observed expected account. A normal desktop browser's existing sign-in is insufficient evidence. |
| `ntlm` | Use an authorized NTLM application with the product-owned browser; prove the actual account and resulting usable credentials. | A suitable application/environment and explicit account observation. No inference from Kerberos, Basic or desktop-browser behavior. |
| `device-flow` | A browser application displays a device code and waits for approval on another device. Complete that approval and observe whether this same journey obtains usable outputs. | A prepared application that owns the device flow, an approval checkpoint and output selection. The seven native page-action types do not establish a separate device-grant polling engine. |
| `client-credentials` | A controlled application obtains a service credential and exposes the selected response to the same journey; prove its service identity at the intended resource. | A reviewed application/journey contract and actual output proof. Do not describe browser navigation as a native client-credentials grant implementation. |
| `refresh-grant` | An application refreshes its token inside one fresh journey and exposes the replacement output. Prove that replacement against the resource. | A controlled refresh checkpoint/output and expected session relationship. Existing session recovery reruns a journey; that alone does not prove a refresh-token grant engine. |
| `dpop` | A resource requires a proof specific to the outgoing request, in addition to its token. Check whether actual product delivery can satisfy a second request with a different target. | A suitable resource and proof-producing configuration. The current injection model copies bearer/header/cookie values; it establishes no request-signing operation. Ordinary bearer acceptance cannot close this assessment. |
| `certificate-bound-token` | Obtain a token associated with a selected client certificate, then prove its use at a protected resource presenting the required certificate. | Resource-side token/certificate association and actual application-request transport. Current mTLS login proofs establish certificate use while obtaining credentials; they do not establish certificate-bound delivery from Burp. |
| `idp-initiated-saml` | Start at an identity-provider application entry rather than the existing client-initiated SAML URL; capture the resulting client cookie and prove its account. | A prepared starting URL and maintained client acceptance. Reuse existing SAML navigation/cookie owners; do not add signature or provider-validation mutations. |
| `websocket-opening` | Send an authenticated WebSocket opening request through the real host and have the controlled application record its accepted account. | Protected handshake acceptance and actual host hook delivery. The existing browser surface owner proves the login-traffic marker reaches a WebSocket opening; it proves neither application authentication nor frame handling. |
| `session-loss-redirect` | An attributed protected request redirects to login when its session is lost. With an explicitly configured matching status, require one recovery and one replay; a rejected replacement must pause. | An actual redirect-loss input with accepting-service/account observations. Reuse the existing recovery owner before adding a browser or Burp test. Status matching exists in `SessionRecovery.matches`; recognizing a particular Location header is a separate question. |

Source review identifies current boundaries without earning passes: `AuthStep.Type` enumerates the seven page actions; `JourneyDefinition.Browser` contains headless/proxy/timeouts; `BrowserFlowRunner.run` constructs a fresh browser context; `JourneyDefinition.InjectionType` contains bearer/header/cookie/disabled destinations. Those facts do not establish operating-system challenge support, device interaction or protocol-specific grant/signing features.

The request-specific proof and certificate-association distinctions follow [DPoP, RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html#section-4) and [certificate-bound access tokens, RFC 8705](https://www.rfc-editor.org/rfc/rfc8705.html#section-3). These references define the assessment question; they do not justify testing an identity provider's implementation.

These recipes add no executions, provider mutation matrix or production feature. New automatic TOTP/approval cases still require the reviewed journey/control contract specified by the [approved matrix](../../designs/authentication-test-lab-cases.md). Scanner licensing, physical-device checks and the existing host specification conflicts remain separate from these sixteen entries.
