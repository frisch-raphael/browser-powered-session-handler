## F07: Successful HTTP status is presented as credential acceptance — historical reproduction; fixed in main

Severity: Low. The actual event row and details say `Application request accepted with these credentials.` The production response handler emits that event for an attributed 2xx response when no configured session-loss rule matches. A 200 login page can satisfy that condition; the extension has no independent proof that authentication succeeded. The journey summary also uses `Request accepted` for this state.

The user requested neutral wording. Recommended event: `Request using this journey's credentials returned HTTP 200.` Include the actual status; do not imply verified login. The captured-credentials event remains a separate observation. Update the existing diagnostic/event presentation owner when production adopts the wording; do not introduce a second browser matrix. This is a presentation finding, distinct from the resolved extraction-only F03 behavior. Production code has not been edited in this worktree.

The controlled lab's positive results are stronger than that event: its protected route checks actual bearer/cookie registry membership, expiry, account, credential role and common issuance. Its public response then supplies the account, issuance and accepted roles. No production status message substitutes for that proof.
