## Expansion and interpretation

This matrix turns the earlier [coverage inventory](coverage_candidates.md) into finite execution definitions. Each named variant gets the execution ID `<group>.<variant>`. Axis rows expand the explicitly stated Cartesian product and put each axis value in the execution ID. Required capability is evaluated per variant, not by blocking an entire group when a baseline variant is independently runnable. Profiles select and deduplicate these IDs; they do not multiply them by every layer.

There are **40 groups and 962 planned requirement/assessment entries** for the initial Windows artifact: 922 automated requirements, 24 host-specific manual entries and 16 manual capability assessments. These are catalog counts, not 922 new tests, passing tests or a promise that all capabilities exist. Existing tests may own several entries through one execution; new code is needed only for missing assertions. Additional platforms multiply only applicable artifact/host executions. The author's proxy-authentication exclusion removed two earlier entries; it is not a runtime-budget reduction.

Variant strings are data labels, not new production settings. The adapter renders native references/output selectors from the approved production contract. Cases that require an absent contract stay blocked. In particular, the tag matrix's 48 ordinary representable cases do not select new multi-output syntax. CORE.recovery's 80 cases are policy assertions with controlled runner/transport boundaries; RUN.recovery and H03 establish distinct real-browser and real-host facts.

The [existing-test ledger](existing_test_audit.md) is preliminary because `java-playwright` is still being developed. Before implementing/scheduling production entries at P2, rerun the complete audit against the actual integrated revision and replace these provisional bindings with current assertion/input witnesses. Extend only verified gaps; do not duplicate an existing owner. A stale/source-only match is not a passing result. The requirement domain is separate from the eventual number of reused/new executions.

## Required interactions and observation boundaries

* Configured upstream proxy authentication is outside the lab scope, including support, bad-credential/challenge handling and rejection/configuration tests. Do not replace the removed cases with negative tests. The mTLS proxy's internal per-attempt credentials are a separate retained requirement; application HTTP Basic/Digest capability assessments are also separate from upstream proxy authentication.
* Assign the browser-visible OIDC client, backend-only OIDC client and SAML client different saved journeys. Every combined automatic case still gets its outputs from one journey. Explicit multi-identity tag slots are checked through production parsing/selection; they are not inputs to combined automatic authentication.
* FED.broker.combined-outputs is the targeted federation/redirect/multiple-output interaction. CORE.lifetime.late-old-401 and CORE.outputs.late-retired-attempt cover version ownership. RUN.recovery supplies actual browser evidence; H04 owns actual proxy-interception recursion.
* Every acquisition success checks protected access. Browser-only fixture validation cannot substitute for invoking the production runner. Provider/client negative controls validate their target and are labelled accordingly.
* FED.negative.code-expired and FED.saml.expired use the observed protocol expiry and real-provider/client timing, with an explicit case budget. A fixture-clock jump cannot establish those claims. If the selected validity period exceeds the case's declared budget, report a prerequisite/budget failure rather than call a runner timeout an expired-assertion rejection.
* CORE.resources unload/backoff tests and RUN.recovery.cancel-cleanup retire pending work before completion. Paused-state cases also observe continuing demand while the coordinator is still alive; shutting it down first cannot prove that pause prevented a storm.
* H02 checks a case-owned sentinel with a positive control. Any decrypted application bytes fail the non-delivery assertion, including malformed requests. TLS preconnection/handshake observations remain separate.
* CAP.assessment entries are deliberately unpromised. Supply operator recipes and capability conclusions rather than invent production challenge solving, integrated-authentication support or protocol grant engines. TOTP/delayed-approval can be promoted to automated cases only when a reviewed journey/control contract establishes them. Physical-token verification is additional manual evidence under TLS.mtls and CORE.retry; SoftHSM does not satisfy it.

## Runtime accounting

The implementation emits one expanded row per execution, with estimated startup/case/teardown time and later observed duration. Group setup is counted once per owned environment, not once per assertion. Serialize real-provider/session resets and browser cases by default; explicit concurrency cases control their own batch. There is no measured total runtime yet. The catalog must expose counts of runnable, blocked, manual, unsupported and unassessed entries, and a selected profile cannot turn missing evidence into a pass.
