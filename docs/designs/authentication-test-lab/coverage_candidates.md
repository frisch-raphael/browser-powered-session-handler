# Authentication test lab: proposed coverage

* **Author:** rfrisch
* **Date:** 2026-11-04
* **Status:** Assistant proposal for EGM discussion and Goldfish review. No implementation approval or passing-test claim.
* **Working hypothesis:** [Concepts brief](concepts_brief.md).

## Purpose and evidence

The lab should establish that the extension obtained, selected and supplied the intended authentication material, including recovery under failure and concurrent traffic. A fixture's successful login response is insufficient. Each scenario needs a protected request that proves the result, and negative controls that would fail if the fixture accidentally accepted anything.

Every named case should specify its prerequisites, journey/selected outputs, request template, expected identity and credential relationships, expected accepting service, expected login count, expected original/replay counts, expected application action count, and the evidence needed to distinguish success from an accidental pass. Use known fixture identities and nonsecret issuance/session identifiers; do not record raw tokens, passwords, PINs, authorization codes or SAML assertions in diagnostic logs.

Keep four evidence levels distinct:

| Evidence level | What it establishes |
| --- | --- |
| Fixture checks | The target enforces its scenario, including failure and identity/session rules. |
| Real browser checks | Actual cookies, redirects, JavaScript and browser restrictions work as intended. An HTTP client following redirects is insufficient here. |
| Production-extension checks | The real runner/coordinator/parser selects outputs, shares authentication work, handles deadlines and closes owned browsers correctly. |
| Real Burp checks | Actual tool requests are changed, stopped or replayed as specified, with observable original/replay behavior. |

A missing browser, provider, supported Burp version or hardware device is a blocked/skipped case, never a passing scenario. The partial Python lab written before EGM clarification provides none of the missing production evidence.

## Candidate checks

The rows below are independent test ideas. Each semicolon-separated variant should receive its own case ID when the reviewed matrix is finalized. Proposed cases do not silently expand the extension's supported extraction methods or protocols.

| Family | Candidate checks | Required evidence |
| --- | --- | --- |
| Basic journeys | Direct form login; username and password on different pages; CSRF hidden input plus required cookie; JavaScript-submitted form; consent/interstitial before completion; invalid credentials. | Expected protected identity, required steps actually exercised, no token publication on rejection. |
| Redirect journeys | No redirect; one redirect; several same-origin redirects; redirects across independent origins; a cookie required at each intermediate step; final callback returning to the original deep link. Exercise GET redirects, POST-to-GET transitions and method-preserving redirects where the fixture uses them. | Ordered hop/checkpoint evidence. Removing any required intermediate cookie prevents completion. Expected final method and destination. |
| Redirect failure | Missing callback; wrong return destination; missing correlation state; redirect loop; unreachable intermediate origin; user cancels before callback. | Finite failure, no usable result published, owned browser cleaned up, no spontaneous browser reopening. |
| Cookie selection | Authentication-server cookie, application cookie and unrelated cookies issued together; an initial decoy cookie replaced after login; same cookie name at different paths; same name on different domains; deletion/expiry during a redirect; ambiguous extraction selectors. | The explicitly selected applicable cookie is used. An early decoy is not published; ambiguity produces a useful failure. |
| Browser cookie behavior | Host-only versus domain cookies; path restrictions; Secure and HttpOnly; SameSite Lax/Strict/None under top-level navigation and cross-site POST; a genuinely cross-site flow rather than merely two ports on one host. | Browser-observed acceptance/sending and protected access. Negative variants explain intentional browser rejection. |
| SSO cookie as output | Extract the IdP cookie and explicitly send it to an IdP protected/session endpoint; use it for a new authorization request without another password submission; remove it or substitute another user's cookie; send it to the wrong accepting service. | Expected IdP identity, zero additional credential submissions on successful explicit SSO use, failure without the required cookie. Do not bootstrap later authentication contexts from that output. |
| Application cookie as output | Extract the client cookie after federation; use it independently on a protected client page; replace it with the IdP cookie; test app-session logout while IdP session remains valid within the same active browser context. | Correct application identity; IdP-cookie presence alone does not count as a client session. |
| OAuth authorization code | Browser receives a code, client exchanges it, resulting access token works at the API; PKCE-enabled client; single-use and expired codes; mismatched state or verifier; wrong client/callback. | Successful resource access and code-exchange evidence. Negative controls do not issue usable credentials. The code itself must not be mistaken for the access token. |
| OAuth/OIDC output selection | Access token versus ID token, refresh token, authorization code and token-shaped decoys; two clients with different API audiences; nested token JSON; multiple token responses during one journey. | The selected access token works at its intended API; unrelated token-like values do not make the test pass. This is fixture discrimination, not a new promise that the BApp validates all protocol semantics. |
| Browser-visible versus backend exchange | SPA performs the exchange in browser-visible traffic; a backend client performs the exchange server-to-server and returns only a client cookie. | Extract only material actually visible through supported browser extraction. Backend validates its own token use; the extension must not claim to extract a hidden access token. |
| SAML | Service-provider-initiated login with redirect to IdP and form POST to the assertion consumer; IdP-initiated login if included in reviewed scope; preserved RelayState; client-cookie issuance; invalid/expired/replayed or misaddressed assertions as negative controls. | A real SAML consumer accepts the valid flow and establishes the expected client session. The extension follows the browser flow; it does not need to parse SAML. A simulated redirect called SAML is insufficient. |
| Brokered federation | Client -> OAuth/OIDC provider -> upstream SAML IdP -> provider -> client; intermediate cookies and return state; upstream rejection/cancellation. | Full ordered flow and final usable application/API credentials, with no shortcut directly minting a token. Proposed additional interoperability case, not a prerequisite for every basic test. |
| Multiple outputs from one journey | Bearer only; application cookie only; IdP cookie only; two required application cookies; bearer plus application cookie; bearer plus two cookies. Check output destinations individually and mandatory subsets together. | Every required output works and belongs to the expected account/session. Remove each mandatory member separately and expect rejection. Do not assemble a combined automatic identity from independent journeys. |
| Output publication and freshness | JSON token arrives before final cookie; final cookie rotates after an intermediate one; one required output is absent; one expires first; refresh changes all outputs; an old attempt finishes late. | Publish a complete consistent set or report failure. Never combine a new bearer with an old cookie or a late result from a retired attempt. Exact multi-output contracts require the revised production design. |
| Same-account session binding | Log in twice as the same account; pair bearer from login A with cookie from login B; refresh only one artifact deliberately; compare with a valid same-session pair. | Same username is insufficient: the strict scenario accepts only artifacts from its required common login session. Independent-cookie scenarios can have different declared rules. |
| Identity selection | Several accounts using identical cookie names and the same login host; same account in distinct journeys; user/admin switches; concurrent Alice/Bob logins; repeated alternating requests. | Nonsecret server assertions identify the actual subject, credential slot and issuance. Deliberately substituted/duplicated values fail the expected tuple. Cross-user cases test extension routing, not general application authorization. |
| Tags | One reference; two/three repeated references to one output; several outputs of one journey; distinct saved identities in independent request slots; repeated sends of one editable template; case-only alias spelling and display-name changes. | Exact expected output per slot, consistent snapshots, no unwanted duplicate acquisition, preserved editable templates. Multiple-tag tests do not reintroduce automatic credential composition across independent journeys. |
| Tag failures and limits | One valid plus one unknown/deleted/ambiguous/failed reference; malformed structure; incomplete output selection; nesting/size/reference limits at and above the supported boundary; output containing literal native-tag text. | Invalid structures fail before login where possible. A failed explicit reference produces zero protected-origin hits, with no literal or partially substituted tags transmitted. Token output is not parsed again. |
| Placement and encoding | Header values, supported text bodies, path and query; URL/form/JSON wrappers; reserved characters, spaces, Unicode, quotes and newlines; nested wrappers; unrelated request bytes; binary/unsupported bodies and invalid header output. | Destination receives the exact intended decoded value, unchanged unrelated bytes and corrected body length. These are synthetic transport oracles, not claims that OAuth recommends placing real bearer tokens in URLs. |
| Automatic injection | Bearer, cookie, and the agreed same-journey combined set; stale pre-existing values; unrelated cookies preserved; duplicate cookie-name handling; enabled/disabled maintenance; tool and URL filters; selected-journey changes. | Required credentials applied exactly once to intended requests. Tagged requests retain their agreed precedence. No accidental shared-cookie-jar identity contamination. |
| Output origin boundaries | IdP, client and API have distinct accepting endpoints; same-host and different-host variants; an unrelated origin deliberately receives a test request. | Each scenario states exactly where its outputs are intended to be injected. Detect wrong-output/wrong-destination use; do not silently invent per-output scoping rules before the production contract is agreed. |
| Lifetime and refresh | Fresh token; exact expiry; refresh skew; opaque cookie lifetime; server revocation before expiry; token remains usable while background refresh runs; failed refresh with still-usable old credentials; stale 401 after a newer result was published. | Correct protected access at each boundary. No serving expired material, premature invalidation or replacement-token loss caused by a late response. |
| Recovery and replay | Configured status match; configured body match; session-loss redirect if supported; no match; maintenance disabled; successful recovery; replacement also rejected; login fails; unrelated timeout. Include POST with a controlled action counter. | One permitted recovery episode and at most one replay per original. Failed replay pauses recovery. Rejected original causes no fixture action; accepted replay causes exactly one. Timeout alone causes no replay. Keep both responses visible. |
| Paused-journey feedback | Journey exhausts allowed network attempts or replacement credentials are rejected; subsequent ordinary requests and explicit tags depend on that journey; tester switches journeys, inspects the failure and invokes Test authentication. Include a healthy unrelated journey and an invalid tag reference as controls. | The author requires a clear, discoverable failed/paused indication naming the journey, explaining the known cause and impact on both paths, and offering explicit recovery. With no usable credentials, ordinary requests continue unchanged with a warning and explicit-tag requests stop; feedback states the actual outcome. Neither path starts another browser while paused. Distinguish active retry from pause, preserve other journeys and verify status updates on explicit testing. Save alone does not clear the pause. Exact UI layout and successful-use rearming rules still require drafting. |
| Save versus explicit test | Save edited settings; test the saved journey; explicitly test a paused journey; repeatedly press Test while its cycle is active; finish a successful or failed test after an earlier Burp request failed. | Save validates/persists without login. Test authentication is the explicit login/retry action, subject to shared-cycle and attempt limits. No combined Save and test or separate Retry button is required. Status reflects the result; neither action silently replays previously failed Burp requests. Dirty-editor interaction remains a drafting decision. |
| Replay fidelity | Tagged request after original tags have been expanded; bearer plus cookies; body/path/query outputs; custom method and headers; large supported body; repeated user resends; replay with an already superseded token; cancellation during recovery. | Reconstruct from the intended template/credential provenance, not by blindly replacing arbitrary matching token strings. Preserve non-authentication data. Verify real host behavior before choosing a replay mechanism. |
| Authentication storms | Many cold requests for one journey; many rejected responses for the same token; several distinct journeys; timer plus manual Test plus incoming requests; login requests passing through Burp; repeated rejection under continuing traffic. | Shared cycle, bounded actual browser creation and cleanup, no recursive cycles, no timer bypass of a paused state. Count browsers/contexts as well as login HTTP requests. |
| Temporary network retries | Temporary network failure then success on attempt two; two failures then success on attempt three; three consecutive failures; concurrent callers joining the same failing journey; cancellation or deadline expiry before retry. | At most three attempts total, initial included, shared across callers and sequential per journey. Stop on success. No fourth attempt within the episode; no replay without replacement credentials. Rejection of the replacement does not restart the network allowance. Observe attempt cleanup and continuing traffic/timers. |
| Failure timing and resources | Slow form, delayed token, connection reset, temporary 503, permanent rejection, cancellation, worker queue saturation, per-request timeout, disabled/finite waiter limits and unload during queued/running/backoff work. | Deadlines remain finite; permitted retries bounded; reservations/resources released; unaffected callers continue; late results cannot publish. Only positively classified temporary network failures receive the agreed initial attempt plus at most two retries; exact classification/backoff remains to be specified. |
| Browser surfaces | Login response before navigation settles; popup/new tab; iframe; fetch/XHR; cross-origin fetch/preflight; service-worker-controlled requests; WebSocket opening request if delivered to Burp HTTP hooks. | Capture supported token responses and classify owned traffic without corrupting CORS or normal User-Agent behavior. Full WebSocket frames are outside the earlier design's scope. |
| Fresh browser state | Journey run A leaves IdP cookies, application cookies, local/session storage or a worker; run B starts; user switches between attempts; cancelled attempt leaves artifacts. | Each new attempt starts clean and does not silently authenticate using run A's browser state. Explicit cached output-token use is distinct from seeding a new browser context. |
| Proxy and TLS | Direct journey; explicitly configured unauthenticated proxy; HTTP and CONNECT; unavailable proxy; untrusted/wrong-host TLS; auth traffic through Burp with interception enabled; internal credentials on the extension-owned mTLS proxy. | Correct route, actionable failure without direct fallback, no recursive authentication, internal mTLS-proxy binding/credential stripping where applicable, no global Burp interception changes. Configured upstream proxy-authentication tests are excluded by the author's later instruction, including rejection tests. |
| PKCS#11/mTLS | Expected client certificate; two same-CN certificates; missing/ambiguous certificate; rejected/unknown-outcome PIN; token unavailable; mTLS redirect between allowed origins; mTLS followed by bearer/cookie use on a non-mTLS resource; direct and explicit-proxy paths. | Server-observed certificate fingerprint and subsequent token-backed identity. Provider/session isolation and cleanup. SoftHSM evidence is separate from physical-device support. Ordinary journeys do not initialize the native layer. |
| Registry and lifecycle | Alias conflict/retirement/reassignment, import/export, missing unremembered secrets, journey edit/delete during login, library changes, reload/unload and fresh packaged startup. | Pure storage/parser checks belong in production unit tests. Integrations verify no request silently switches identity and no browser/provider/listener survives its intended lifetime. |

## Checks that prevent misleading passes

1. A basic fixture issues fresh credentials with real expiry, rather than accepting a static string that already expired or never changes.
2. Each credential carries server-verifiable account, credential-kind and issuance/session ownership. Evidence reports safe identifiers, not the raw credential. Do not universally require two different journeys to have unequal strings: equality alone is not proof of a defect. Fixtures deliberately issue distinguishable values where the case needs to detect substitution.
3. Mandatory combinations are checked with each member missing, replaced, expired and paired with another session. Acceptance rules belong to the case rather than one universal mixed-identity rule.
4. The server tracks requests separately from successful protected actions. Zero actions is not evidence of zero requests. A tagged stop requires zero protected-origin request hits.
5. Browser-creation evidence comes from the production runner/owned-process instrumentation. Server login counters alone cannot detect a browser opened without reaching the server.
6. Recovery traces distinguish the original request, each shared authentication attempt and the one replay per original, without exposing secrets.
7. A server-side-only OAuth access token is never reported as an extension extraction success. Protected client-cookie access is the browser-visible outcome for that fixture architecture.
8. SSO-cookie presence is not proof of SSO: explicitly using that extracted cookie must establish the expected IdP identity without resubmitting a password. A later authentication attempt still starts clean.
9. Cookie tests distinguish cross-origin from cross-site and include HTTPS where attributes require it. Changing a port alone does not create all cookie-boundary conditions.
10. Real provider validation and small controlled fixtures serve different purposes. Negative protocol cases ensure fixture authenticity; they do not turn this lab into a general-purpose OAuth/SAML vulnerability scanner.

## How to turn the ambition into a finite matrix

Proposed strategy, subject to EGM review:

* Enumerate every supported output choice and every nonempty required subset of a declared same-journey output set. For a three-output fixture this gives seven subsets. Explicitly declare which services accept which subsets; IdP and client cookies are not universally interchangeable requirements of one API.
* Exhaust the identity/session substitutions for the small configured fixture population. Include repeated output references and the same-user/different-login cases; do not test only Alice versus Bob.
* Run every supported login-flow family with its applicable extraction modes and at least one actual protected-resource check. Run combined-output publication cases on flows that produce those outputs.
* Cross the supported tag locations with applicable encoding modes, one/two/three references and boundary cases. Keep unsupported combinations marked unsupported rather than inventing behavior.
* Cross the recovery cases with automatic versus explicit-tag requests, single versus combined outputs and single versus concurrent demand. Separately establish real-tool behavior for each supported Burp tool.
* Add targeted higher-order cases: brokered redirects plus cookies plus combined outputs; concurrent recovery plus late 401 plus replacement publication; proxy self-traffic plus active interception; cancellation/unload during retry/backoff.
* Keep fixture, browser, extension, Burp and optional hardware results separately reportable. Every design requirement maps to case IDs or an explicit unresolved gap. State tested combinations and excluded combinations; do not label sampled coverage exhaustive.

## Capabilities to classify before making support claims

These are additional authentication situations worth retaining in the inventory. They need a deliberate supported/unsupported/manual classification rather than an automatic v1 promise:

* TOTP or other multi-step second-factor prompts, delayed out-of-band approval and explicit rejection/timeouts. Deterministic test-only factors can validate journey waiting; real-device prompts require separate evidence.
* WebAuthn/passkeys, CAPTCHA and human-presence checks. Recording a browser journey does not establish unattended support or authorize bypassing challenges.
* HTTP Basic/Digest, integrated Windows authentication and Kerberos/NTLM. The earlier bearer/cookie injection design does not automatically support these mechanisms.
* OAuth device authorization, client credentials and refresh-token rotation. Browser-login support does not imply a generic OAuth protocol client or refresh-grant implementation.
* Sender-constrained tokens such as DPoP or certificate-bound access tokens. A raw copied bearer value may not be sufficient; the lab should expose this boundary without claiming that credential extraction implements the required proof.
* Logout at the client versus logout at the IdP, back-channel revocation and an application returning a login page with HTTP 200. Declare the configured session-loss rule and expected recovery in each included case.

## Author addition: diagnostic accuracy (2026-11-05)

Test the actual production output shown to the user against an independently controlled outcome and known stage/cause. In particular, a missing selected cookie after completed response delivery must not be reported as a connection failure. Contrast those two conditions and cover ambiguous/missing outputs, response parsing, journey-step failure, confirmed login rejection, protected-use rejection, unresolved references, unavailable prerequisites, cancellation, retry exhaustion and stale/current success state. Unknown causes must stay uncertain; successful extraction alone does not establish protected access.

The [diagnostic contract](../../designs/authentication-test-lab-cases.md#user-visible-diagnostic-contract) expands this addition into 18 requirement variants. Check the actual summary/details/status and applicable request feedback, safe attribution, revision/attempt freshness and secret redaction. Existing `DiagnosticsTest`, editor/state tests and failure witnesses remain provisional owners until the fresh P2 audit; extend only missing assertions. H02/H05 retain their distinct real-host wiring obligations without repeating this matrix through Burp.

## Recommended shape for review

Use one catalog/startup entry point while allowing several cooperating roles: client applications, an identity provider and protected resources. Controlled fixtures provide precise faults, clocks, gates and counters. The author selected Keycloak's official `quay.io/keycloak/keycloak` container image for real OAuth/OIDC and SAML interoperability, with preconfigured fixture users and clients. Small client apps and protected verification endpoints complete those cases. Controlled fault fixtures remain separate. Exact image version/digest, client dependencies and hostname/HTTPS/process topology remain to be designed; basic controlled fixtures need not require Docker.

Keycloak supports brokering via OIDC and SAML providers, allowing the complex federation scenario to use an additional realm or instance instead of a custom protocol implementation. The choice of topology is still open. Realm import provides repeatable initial configuration, but rerun/session reset still needs its own specified behavior; a restart must not be assumed to clear an existing provider session or overwrite an existing realm.

Prepare named scenario recipes, selected-output definitions, importable native journey examples once the multi-output schema exists, request templates, expected protected identities and evidence instructions. Avoid baking the abandoned one-token API/Hackvertor format into the new lab. Preserve the user's existing mTLS assets and environments.

Implementation choices should wait for EGM review and author agreement. Multi-output selection, origin targeting, replay host feasibility, recovery rearming and temporary-failure classification/backoff are production-design questions that a fixture must not silently decide. The author has settled the numeric distinction: one shared recovery episode can contain at most three sequential authentication attempts for temporary network failures, including the initial attempt, and each original application request still has at most one replay.

## Sources for protocol-derived candidates

The following sources motivate fixture behavior; the larger extension/test recommendations above are engineering proposals.

* [OAuth 2.0 authorization code flow, RFC 6749 section 4.1](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1): separate browser authorization response, client code exchange and access-token response. This motivates exercising the actual exchange and distinguishing browser-visible from backend-only results.
* [OAuth security best current practice, RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html): PKCE, code replay prevention, redirect validation and token audience restrictions motivate negative controls and wrong-output/wrong-resource checks. These are not assertions that the BApp performs IdP-side validation.
* [SAML 2.0 Profiles, section 4.1](https://docs.oasis-open.org/security/saml/v2.0/saml-profiles-2.0-os.pdf): browser SSO, assertion consumer behavior, correlation and recipient/time constraints motivate real SAML flow checks rather than an OAuth code flow relabeled SAML.
* [MDN Set-Cookie reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie): cookie domain/path, Secure, HttpOnly and SameSite behavior motivate actual-browser selection and cross-site tests. Fixture attributes must match the intended deployment and expected browser behavior.
* [Keycloak container guide](https://www.keycloak.org/server/containers), [application/protocol overview](https://www.keycloak.org/securing-apps/overview) and [identity-brokering guide](https://www.keycloak.org/docs/latest/server_admin/index.html#_identity_broker): official container, realm import, OAuth/OIDC/SAML application integration and brokered federation support. The author selected this provider after the first Goldfish round; the selection has not yet received a follow-up review.
