# Create journey steps by interacting with the browser

* **Author:** rfrisch
* **Status:** Implementation in progress - shared fixtures, launcher and action support qualified; private recorder in progress; recording UI not delivered
* **Date:** 2026-11-07
* **Updated:** 2026-11-08

## Overview

Allow a Burp user to create login journey steps by performing the login in a visible browser. The resulting steps appear in the existing Login steps editor, where the user can inspect and edit them before testing replay. This extends the Java-owned extension and its installed Burp Browser and bundled drivers.

This design uses the bundled Playwright recorder through a version-pinned Java adapter for form controls, frames and popups, and replacement of the current step sequence after review. Password inputs become secret steps with their recorded values retained; explicit context-switch steps control page and frame targeting.

## The Problem

Today the user selects each action and enters its target selector in the Login steps editor. Recreating a login this way requires translating visible page interactions into automation settings. Incorrect selectors and missing actions become apparent only when the user tests the journey.

Recording could reduce that translation work, but a successful manual login does not prove that the result can run again. Page state, changing selectors, redirects, frames, popups and one-time challenges can make a recording incomplete or unsuitable for replay. The feature must make these limits visible instead of presenting a recording as a verified journey.

## Goals

* Let the user initiate browser-based step creation from the journey editing workflow and perform the login actions directly in a visible browser.
* Turn supported interactions into ordered, editable journey steps, without requiring the user to write Playwright code.
* Let the user inspect the proposed steps and understand unsupported interactions before relying on the journey.
* Keep existing steps and secrets unchanged until Apply; make replacement undoable and reject stale recording results.
* Handle typed secrets under the existing session-secret, Remember secrets and export-consent rules. Keep secret values out of step summaries, event logs and diagnostic output.
* Verify the resulting journey through the existing Test login workflow in a fresh browser context; recording alone is not proof of replay success.
* Keep browser work off Swing's event dispatch thread and support cleanup on cancellation, browser closure and extension unload.
* Preserve universal offline delivery and reuse the existing authentication lab and federation fixtures for acceptance coverage.

## Non-Goals

* Replace the existing manual step editor or require a separate scripting language from the user.
* Automatically solve CAPTCHAs, approve external MFA prompts or make one-time credentials reusable.
* Infer credential capture rules or automatic HTTP injection settings from browser interactions in this feature.
* Change the extension into a general-purpose browser testing or macro-recording product.
* Require users to install Node.js, Python, a browser automation skill or a separate browser to use the delivered extension.

## Open Questions

* Qualify the password-metadata hook beyond its successful isolated Windows cases, including cross-origin nested frames, shadow DOM, composition/autofill and replacement-element continuity. The native fill payload lacks a password flag; never default missing metadata to ordinary saved text.
* Qualify the selected private adapter in the managed headed browser with proxy/User-Agent guarding, mTLS, nested cross-origin frames, navigation, Stop, popup review and cancellation. The isolated synthetic probes do not establish these results.
* Complete the implementation qualification checks below. The revised readiness audit returned five distinct findings; their design responses are recorded in the current report. The post-audit changes have not received another independent audit, and there is no clean-readiness or product-acceptance verdict.

## Technical Plan (Architecture)

### Existing implementation and constraints

The extension declares Playwright Java 1.64.0 in `bapp/build.gradle.kts`. `AuthStep` currently supports click, ordinary input, secure input, and four wait actions. `BrowserFlowRunner` executes element actions through `page.locator(selector)` on one page. It does not currently represent a frame path, popup selection, keyboard action, dropdown selection or explicit checkbox state. Recording those actions therefore requires either an explicit unsupported-action outcome or an extension of the step format and replay engine. Translating them silently into clicks is not an accepted equivalence.

`JourneyDraft` retains incomplete settings and limits a sequence to 256 steps. Secure input values are excluded from its step records. Journey contracts live under `bpsh.journey`, editing under `bpsh.journey.editing`, and Swing under `bpsh.burp.ui`. `JourneyWorkspace` owns edits and publication; `JourneyStorage` owns persistence and revision checks. `UiController` captures and presents editor state. Recording results must pass through those ownership boundaries rather than writing configuration directly from a browser callback. The detailed file inventory must use these current paths.

The current authentication runner requires a complete executable journey and returns captured credentials. Recording begins before a user has finished those settings, so calling its normal authentication method is not sufficient. Recording and authentication share the browser-session launcher described below.

### Recording mechanism: private Playwright APIs selected by author

Use the recorder already implemented in the bundled Playwright driver. The public Java API does not expose recording, so access the driver's internal `startRecording`, `stopRecording` and `recorderEvent` messages through a narrowly scoped Java adapter beside the current driver bootstrap. Do not implement a second general DOM interaction recorder or parse generated Playwright source.

Pin **both** Playwright Java 1.64.0 and driver-package 1.64.1, as recorded by the existing asset lock. The Java dependency version is not the driver package version. The internal protocol is unsupported as a public compatibility contract and must be tested on every dependency upgrade. Validate commands/event shapes and fail the recording with safe incompatibility guidance when they differ; no silent fallback to custom recording, downloads, a system browser or another driver version.

The 2026-11-08 isolated Windows probes used existing cached artifacts and received structured fill, updated-fill, checkbox and click events, frame-entry targeting and a popup signal. Stop completed and a subsequent click emitted no recorder event during the observation period. The probes required no TypeScript build, new runtime, Inspector window, modified driver or Playwright fork. This establishes a feasible transport route, not full product acceptance.

The recorder owns interaction detection, native selector generation and action merging. Java owns the private transport boundary, action normalization, target/context translation, secret classification and lifetime, native review, persistence and replay. Events include generated source and accessibility snapshots: discard those fields at the adapter boundary and never persist, export or log them. They may contain entered values. No source-code parser or evaluator is part of this design.

The author accepts version-specific maintenance of this private interface. If integration later requires broad driver patching or general event-capture duplication, stop and revisit the design; that is not implied permission to fork Playwright.

### Selected interaction scope

Support common form controls, nested frames including cross-origin frames, and opener-owned popups that can return the user to the opener. These capabilities require new typed steps, context transitions and acceptance evidence. They are not capabilities of the current runner. External-device authentication and non-replayable challenges remain outside the promise of recording.

### Component boundaries for the selected approach

```text
Burp Login steps editor
  -> recording request and cancellation
Browser recorder (dedicated worker and fresh context)
  -> pinned Java adapter: startRecording / recorderEvent / stopRecording
  -> upstream actionAdded / actionUpdated / signalAdded
  -> Java action conversion and separately owned input values
Journey editing boundary
  -> validate and prepare proposed steps
Burp review UI
  -> apply only to the matching journey/editor revision
JourneyWorkspace / JourneyStorage
  -> normal autosave and publication
Test login
  -> BrowserFlowRunner replays saved steps in a new context
```

The browser adapter owns Playwright handles and its worker thread. Only framework-free recording requests, results, target descriptions and cancellation contracts cross into journey editing and UI. Browser callbacks cannot publish a journey, change its settings or write files. The composition root wires the recorder to the editing workflow; authentication/session policy does not acquire an editing dependency.

Record control state semantically: checkbox/radio desired state, selected option values and keyboard submission must remain distinguishable from a click. Do not record ordinary text typing twice as both key presses and fill actions. Detailed Implementation specifies supported submission keys and upstream action conversion; composition/autofill outcomes require the stated browser tests.

Each recorded action must identify its page and ordered frame ancestry. Use the driver event's context/page references and recorded selector frame path; page-supplied IDs cannot establish ownership. Keep access to private driver references inside the runtime adapter. Obtain the actual opener from Playwright. Suggest an opening action only when the recorded candidate set has one member; ambiguous action associations require a user choice during review. Playwright does not supply a click/key UUID proving which action caused a popup. Replay must register the expected popup before executing the trigger, retain its page identity through redirects, and support subsequent actions on the opener. Never choose a page by current focus or an array index. Persist page and frame targeting as explicit context-switch steps, as specified below.

Nested frame targets must resolve through their ancestry rather than matching a URL across the whole browser. Detached or ambiguous targets fail at the owning step; they do not fall back to the main frame. Cross-origin observation uses Playwright frame APIs, not direct JavaScript access from the parent document. Reuse native recorded selectors rather than writing another selector generator. The source-frame bridge and lexical lowering below have limited Windows evidence. Nested cross-origin frames, popup association and races still need the specified managed-browser lab checks before delivery.

### Certificate setup before login steps

**Author requirement:** configure the optional client certificate before creating or testing login steps. The proposed wizard order is Setup, Client certificate (when enabled), Login steps, Capture credentials, then Test & use. When Client certificate is off, skip that page; retain the existing Setup checkbox as the enable control. Existing certificate discovery, device selection, PIN entry and certificate selection controls are reused, not duplicated in the recorder.

Change the wizard's positional assumptions together: page creation order, Back/Next skipping, optional-page enablement, remembered per-journey page, validation reveal and failure navigation. Use named page identities within UiController rather than scattering replacement numeric indices. Stored journey formats and step IDs do not change because of this presentation reorder. Preserve autosave and incomplete editing; moving between pages must not force unfinished configuration to become executable.

Both Record in browser and Test login use the certificate/PIN already configured for the selected journey. Ordinary local configuration validation can identify an enabled but incomplete certificate setup; it performs no HTTP request or TLS probe. Record needs only valid setup/certificate inputs, not completed steps or capture rules. A server's previously unknown client-certificate requirement is learned from the normal browser connection and reported when it fails. Do not add a preflight request, speculative login, separate certificate probe, automatic enablement or automatic retry that submits a PIN again.

| Observed condition | User-facing message and destination |
| --- | --- |
| Client certificate enabled, no certificate selected | ?Choose a client certificate before recording or testing this journey.? Reveal Client certificate and Choose certificate. |
| Client certificate enabled, configured PIN missing | ?Enter the client-certificate PIN before recording or testing this journey.? Reveal Client certificate and PIN after device discovery. |
| Normal connection positively reports a client certificate is required, Client certificate off | ?This server requires a client certificate. Enable Client certificate in Setup, then choose a certificate and enter its PIN.? Reveal Setup's enable control; the certificate page follows it. |
| Normal connection reports client-certificate authentication failed, none configured | ?Client-certificate authentication failed. Enable Client certificate in Setup and configure a certificate and PIN.? Do not claim a certificate was rejected when none was supplied. |
| Normal connection reports client-certificate authentication failed, certificate configured | ?Client-certificate authentication failed. Check the selected certificate and allowed authentication servers in Client certificate.? Preserve any more specific known PIN/device/certificate error instead. |
| Generic TLS failure without positive client-certificate evidence | ?Could not establish a secure connection. Check the server certificate settings and whether a client certificate is required.? Do not assert that missing client authentication is the confirmed cause. |

Add typed client-certificate-required and client-certificate-failure outcomes to the failure contract. Whitelist exact browser symbols such as `ERR_SSL_CLIENT_AUTH_CERT_NEEDED` and `ERR_BAD_SSL_CLIENT_AUTH_CERT`; the latter can mean a bad or missing certificate, so use the configuration-sensitive wording above. Preserve the existing distinct server-trust, proxy, PIN and device failures. A reset, generic TLS error, timeout, HTTP 401 or arbitrary response text is not proof that mTLS is required. A positive typed failure from the managed TLS path may supply the same attribution; do not retain raw handshake exception text or guess from it.

Use the existing inline guidance and Event log with typed input attribution. An explicit Record/Test failure may reveal the relevant page/control for the same unchanged journey; late or background failures must not steal focus. Keep certificate requirement, trust failure, missing PIN and rejected PIN distinguishable. Recorder failure retains existing steps and releases uncommitted values; the user configures the certificate and explicitly starts recording again.

Acceptance must verify the new page order with Client certificate both on and off, Back/Next and remembered-page behavior, validation/failure reveal after reordering, local missing-certificate/PIN guidance, a mandatory-client-certificate lab server with the option off, configured-certificate failures, unrelated server-trust errors and generic TLS failures. Observe that Record/Test adds no probe request and performs no duplicate authentication/PIN attempt for this guidance. Use the existing lab TLS fixtures and native UI tests.

### Typed-value policy: HTML password inputs are secrets

**Author decision:** classify an HTML `<input type="password">` as Enter secret and retain its recorded value without asking the user to enter it again. Other supported text inputs become ordinary Fill field steps with their recorded values. Do not require a separate classification review for each field. Use the browser's normalized input `type` property, not a literal case-sensitive attribute-string comparison. An observed non-password input type is ordinary input. An absent or invalid HTML type attribute uses the browser's normalized default; that is distinct from unavailable classification metadata. If neither metadata nor inherited known-secret protection establishes the status, keep the value as Enter secret and show the review warning below rather than stop recording.

Consume upstream fill actions as they arrive. An actionUpdated event replaces the associated provisional action, rather than appending another fill or overwriting an arbitrary visible row. Preserve separate fills when upstream emits them around intervening actions. Stop recording uses the upstream stop/flush operation and processes its delivered events before review; tests must verify the final typed value is included without requiring blur or another click. A known delivery failure makes the recording incomplete. Do not require an old document to send a terminal acknowledgment after navigation. Navigation reliability must be established by the browser tests in Detailed Implementation; no event loss has yet been demonstrated.

Once a field has been observed as a password input, keep every captured fill for that same field secret for the rest of that document's lifetime, across edit groups and changes of input type. A show-password toggle must not downgrade later edits to ordinary text. If the page replaces the element and password-field continuity cannot be established safely, retain the replacement fill as Enter secret and flag it for manual review; uncertainty alone does not make the recording incomplete. A field that is only ever observed as text remains ordinary input under the author's selected policy. A custom password widget, recovery code or other sensitive value without password input semantics will not be automatically protected; the existing editor must allow the user to change the resulting step to Enter secret.

Candidate secret values remain separate from nonsecret step records. On Apply, transfer them under the resulting stable secure-step UUIDs into the normal editor/session secret ownership path. Users can immediately test the journey without entering the same password again. Remember secrets remains off by default: retained session values survive within their normal session lifetime, while persistence across restarts follows that existing setting. Export inclusion remains separate consent. Ordinary recorded input follows the normal saved-text behavior. No new implicit persistence consent is introduced by recording.

No entered value belongs in step summaries, event history, raw browser exception output or recording diagnostics. Bound and validate recorder event payloads before accepting them. No recorder payload grants filesystem, storage or arbitrary Java execution access. The final design must also address sensitive option values, selectors and URLs rather than assuming those are harmless.

Owned Java character buffers can be wiped, but transient JavaScript and Java strings created by browser transport cannot be guaranteed erased. No recording policy may promise complete memory erasure. Browser profile persistence, tracing, video, screenshots and generated source must not become implicit recording outputs. The upstream recorder can generate source strings in memory; discard those strings without parsing or retaining them.

### Password identification warnings and manual correction

**Author decision:** inability to classify a captured fill does not stop recording or block Apply. First retain any established secret protection without a new warning. Otherwise default the uncertain fill to Enter secret, retain its recorded value in the existing secret snapshot, mask it in review and show: "Could not identify this field's type. Kept as Enter secret; change to Fill field if it is not sensitive." The existing action picker supplies the correction; do not ask the user to enter the value again or add a mandatory acknowledgment. Changing to Fill field explicitly moves the value into ordinary saved configuration under the existing editor rules. Recording notes remain review-only and are not new executable or persisted draft fields.

If no field was positively identified as a password input during the recording, show one review warning: "No password field was identified. If you entered a password, change that step to Enter secret." This also covers recordings with no fills and password-free login flows; it is informational, not proof that a password was omitted. Unknown fills already have the protective Enter secret fallback. Do not claim that warning text detects a field or value the recorder never observed. Missing actions still require adding a step manually or recording again.

Known password fields and their sticky secret status are unchanged. A later unknown annotation never downgrades a known secret. Showing a known password, editing it afterward or receiving an update to its already secret candidate does not create a classification warning. A replacement associated with an already protected logical target also inherits Enter secret without a warning, under the protection rule below. The warning applies only when neither observed password history nor inherited secret protection establishes the candidate's status. Protocol failures, unsupported operations and observed delivery loss retain their existing outcomes. Qualify no-password-detected, mixed known/unknown, missing/contradictory metadata, manual correction, Apply without correction, Remember secrets, cancellation and Undo through the existing test owners.

### Recorder metadata integration

A 2026-11-08 isolated Windows prototype established a candidate integration without modifying the driver: install a small metadata hook with `BrowserContext.addInitScript` before enabling recording/navigation. Wrap the existing private `__pw_recorderRecordAction` function without replacing its behavior or copying its implementation. When upstream emits a fill, use the currently dispatched input event's actual target, rather than a later selector lookup or the currently focused element, to classify that same action.

The probe uses the Chromium current-event facility (`window.event`) within the private call. This is a version/browser-specific dependency, not a supported cross-browser extension API. If the expected event/target/value association is absent, emit unknown classification. Java first preserves any established secret protection without adding a warning; otherwise retain the fill as Enter secret with a nonblocking review warning. Do not persist an unclassified value as ordinary input automatically. Do not introduce a fallback that guesses from a label, selector text or last focused field. Treat a missing hook or stripped annotation as unknown as well.

Track field identity with a per-document WeakMap and latch password classification in a WeakSet. Observe password input type history, including a change from password to text before the first edit. Attach classification, document identity and field identity to fills as `bpshClassification`, `bpshDocumentId` and `bpshFieldId`; attach `bpshSourceActionId` to each interaction for source-frame association. Do not create another copy of the input value or another interaction stream. Preserve the wrapped function's binding properties and arguments so normal Playwright callbacks still work. Source/page ownership still comes from the driver event, not a claimed identity in page data.

Java validates the annotation and checks established secret protection before adding a classification warning. An unknown fill with no inherited known-secret status becomes a masked Enter secret candidate with its value in the separately owned secret snapshot and a review-only note keyed to the source action; it is not an ordinary persisted draft value. Once an unknown fill becomes a secret candidate, only explicit user correction in review makes it ordinary. A prior known-secret classification remains sticky. For actionUpdated, preserve the field/document association and sticky secret state; a previously secret source action cannot be downgraded by a later ordinary annotation. Strip generated code and accessibility snapshots as already required. The main-world hook is not a security boundary against a hostile target page. Malformed, missing or contradictory classification metadata uses the secret fallback and warning; malformed action/transport data still fails under the separate protocol rules. Acceptance must exercise interference rather than claim tamper-proof recording.

The final synthetic probe observed two ordinary fill events/updates and five secret fills, covering initial password entry, Show password followed by correction, reveal-before-typing, an iframe password and a password after navigation. It used three distinct document identities. The earlier approach that cleared an independent input-event observation in a microtask failed with unknown classification; it is not the selected mechanism. Evidence is in `bapp/build/egm-review/browser-recording/password-metadata-probe.json`.

These results establish a candidate hook for the pinned Chromium driver, not full production qualification. The hook must be bounded and tested for nested cross-origin frames, open shadow DOM, composition/autofill, synchronous page changes, replacement nodes, missing metadata, cancellation and all supported platforms. Closed/opaque targets remain unsupported. Implement the bounded replacement/source-frame policies below and qualify their required cases; do not infer wider support from the synthetic cases.

### Applying the recording: Replace selected by author

The author selected Apply mode 1. Record a complete replacement from the configured Login URL in a fresh browser context. Do not replay the current steps before recording. Keep the current sequence and its secrets unchanged while collecting and reviewing candidates. Apply replaces the sequence as one structural edit and then uses normal autosave; Cancel discards the candidates. Continue/append recording is outside this design.

Capture the selected journey identity and editor revision at recording start. Before Apply, recheck both and the external-storage availability/revision through the existing editing boundary. If settings or steps changed, do not merge or apply the old result automatically. Explain that the journey changed and require a new recording. Allocate new step UUIDs for the replacement; preserve the previous sequence's UUIDs and secret ownership only inside the normal bounded Undo entry. Reject recordings exceeding the total step limit rather than truncating them.

The review must show ordered action types and page/frame targets, without input values in summaries. Password fields remain masked. Unsupported actions, missing values or unresolved page/frame targets must identify what was omitted or needs correction, without claiming a complete replay. Describe known omitted keys and click gestures without echoing selectors, entered values or arbitrary key text. These warnings do not block replacing the captured steps as an editable draft. The review controls and correction/re-recording behavior are specified under Review and native editor behavior and Detailed Implementation.

Cancel discards only the recording; stale results cannot overwrite newer edits or another journey. Recording does not publish credentials to the cache or establish a successful Test login.

### Replacement-field classification policy

The metadata hook keeps per-document identity and known-password history, plus a WeakSet of fields positively observed as ordinary while their root's history was available. Observe child additions/removals and input-type changes, including old attribute values. Before classifying a fill, drain MutationObserver.takeRecords and process that batch in two passes: first record all password/type history and detect removal of a known-password node or a subtree containing one; only then classify newly observed ordinary nodes. This avoids treating a replacement added in the same batch as an unrelated ordinary field before seeing the removal. Retained nodes keep their identity across moves; known password nodes remain secret even when reattached.

Removal of a known-password node sets a replacement-uncertainty latch for the rest of that document's lifetime. A newly observed non-password field after that point has unknown DOM classification even if its current HTML type is text. Existing positively observed ordinary fields remain ordinary; known or currently password fields remain secret. Unknown DOM classification does not itself require a warning when Java can inherit secret protection from an already protected logical target, as specified next. Otherwise use Enter secret with the nonblocking warning. The latch is deliberately conservative: an unrelated field added later can also need manual reclassification. New navigation/document identity resets the latch; a different element ID does not reset it.

**Preserve an already established secret without warning:** retain a browser-owned set of protected logical targets once a fill is positively classified as password. Key it by actual page/frame identity, that frame's document generation and the exact native leaf selector. Obtain ownership through the source-frame binding, not a page-claimed frame ID; clear the frame's target set on navigation/detachment and all sets on recording cleanup. A later fill at that same logical target inherits Enter secret even if its DOM node is new or its current type is text. A source-action update to a candidate positively identified as password retains that protection too. An update to an unknown fallback retains its existing warning until the status is resolved; a masked fallback alone is not proof that classification succeeded. This only carries forward secret treatment; it does not establish DOM-node identity, merge separate fields, repair an unresolved target or permit an ordinary-text downgrade. Preserve separate candidates when the action-update rules require them. Do not match by field value, label similarity, approximate selector or nearest DOM position. Bound this set by the existing 4,096-field/document and 4 MiB metadata limits; exhaustion uses the existing uncertainty fallback.

The user therefore sees no warning for a normal Show password toggle or a replacement that retains an already protected logical target. A new node with a different/unresolvable target and no independently observed password history remains uncertain and receives the existing warning. The same selector in a different frame or document does not inherit protection. Required cases: same-node reveal/edit without warning; new-node replacement at a protected target without warning or value re-entry; an unassociated replacement with warning; and equal selectors in different frames/documents without cross-target inheritance.

Each observed root needs a complete initial scan and subsequent type/removal history before it can establish ordinary fields. A late-discovered open shadow root lacks that earlier history: its existing non-password fields are unknown. Observe that root for subsequent password history; known/current password targets remain secret. Closed or inaccessible targets cannot establish ordinary classification. This is bounded password metadata, not a second interaction detector.

Limit a root scan or mutation batch to 16,384 visited nodes and 4,096 tracked fields per document, with at most 4,096 pending mutation records and the existing recording payload/data caps. Use bounded iterative traversal. If a budget is exceeded or history observation fails, latch degraded history for that document: subsequent fills cannot become ordinary automatically, but retain values as Enter secret with the same warning. Do not silently stop observing and continue producing ordinary classifications. Release observers and metadata ownership on document teardown and recording cleanup. No entered values are added to these sets/maps.

The isolated Windows replacement probe received three ordinary fills, five secret fills and two unknown fills across three documents: replacing a known password node with a differently targeted text node and adding another text field produced unknown, while an existing ordinary field remained ordinary. Evidence: `bapp/build/egm-review/browser-recording/replacement-metadata-probe.json`. This measured DOM classification, not the later protected-logical-target rule. That rule, scan budgets, shadow-root history and remaining replacement timings have not been qualified by this probe. Add the required cases above and exact shared-lab cases for same-batch and reordered remove/add, subtree replacement, type changes before first fill, detach/reattach, late shadow roots, budget exhaustion, navigation reset and the user's no-re-entry warning/correction flow.

### Target representation: explicit context-switch steps selected

The author selected Representation B. Ordinary actions execute against the current page/frame context. Existing journeys start on the initial page's main frame and retain that behavior. The editor includes context-switch rows alongside interaction and wait rows; summaries identify transitions without entered values.

The sequence needs operations for declaring an expected popup before its trigger, switching to a named page, entering a child frame, returning to a parent/main frame and closing a page. A popup declaration binds its logical page reference to the current opener and expected creation, with bounded waiting at the point that page is needed. All page observation listeners are installed before user actions run. The declaration must not synchronously wait before its triggering click has executed. Browser observations establish opener ownership. The recording review resolves the opening action when it is ambiguous; An unresolved relationship remains visible and may be completed before or after replacement; Test login requires a valid relationship. Missing opener identity, unsupported creation or ambiguous page identity cannot be repaired by guessing.

Switching pages resets the active frame to that page's main frame. Enter frame resolves one child frame through its owning iframe element within the current frame. Parent/main transitions must not retain detached frame handles. Closing the current page leaves no active target until an explicit switch chooses a live page; no automatic choice of the opener is implied. The recorder inserts the required switch when the next observed action returns to the opener.

Validate references and context transitions in the shared journey compilation/codec boundary. Prevent duplicate page declarations, unknown page references, impossible parent transitions and action execution without an active target. Dynamic absence/detachment remains an attributed runtime failure. Moving or deleting context steps can invalidate following actions; retain unfinished edits under existing draft rules and identify the affected step when execution is requested. Reuse stable UUIDs for failure attribution and secret associations.

The exact wire fields and backward-compatible version-1 encoding are specified in Detailed Implementation. Existing documents must continue to load; new operations must fail clearly in versions that cannot interpret them rather than executing against the wrong context.

Use deterministic popup relationships and frame locator ancestry rather than browser focus, page-list positions or recorded absolute frame URLs. Cover codec compatibility, manual editing and indexed step failures.

### Browser setup boundary: shared launcher selected

The author selected Boundary A. A browser-owned session launcher acquires verified assets, optional PKCS#11 identity and transport, traffic provenance, driver, browser and context. Its returned lease is owned and closed by the calling worker. Setup failure closes everything already acquired. Authentication and recording use the same launcher and transport rules; neither workflow constructs its own alternative proxy path.

The launch request is independent of a complete executable journey: validate the Login URL, timeout, configured proxy and enabled certificate settings through shared compilation/validation logic. Recording must not require valid old steps, capture rules or a unique executable tag alias. Do not bypass certificate allowlists, trust configuration, proxy URL restrictions or PIN suppression policy. Credential-capture validation remains necessary when the user later runs Test login.

The launcher accepts explicit headed/background mode and cancellation/deadline contracts. Recording requests headed mode without saving that override. Authentication keeps its existing deadline, admission, retry, cancellation and cache-publication behavior. Recording is an explicit editing operation with its own bounded interactive lifetime; it must not reuse the short authentication deadline or hold an authentication admission permit while the user types. Duration and concurrency limits are specified in Detailed Implementation.

Do not invoke full authentication with fake credential extraction or dummy steps. Recording and authentication share the launcher, while retaining their separate workflow responsibilities.

### Launcher input PIN ownership

The shared launcher receives `BrowserSetup` and a borrowed `SecretStore.Values` snapshot separately, along with visibility, deadline, cancellation and progress. `BrowserSetup`, recorder requests' nonsecret metadata and action payloads contain no PIN. Authentication supplies its existing attempt snapshot. Recording captures an independent session snapshot containing the configured PIN and no old step-secret values; it does not require old steps to be executable.

The recorder owns that input snapshot from successful worker enqueue until preparation returns or fails. If enqueue is rejected, close it immediately. The launcher borrows the snapshot and obtains its own independent PIN character array through `pin()`. Wipe that array in finally after identity selection returns or throws. The existing Pkcs11IdentityManager clones the PIN for its queued native operation and retains/wipes that separate owned copy only when the actual operation ends, including when the caller has already timed out or cancelled. Preserve that behavior rather than erasing an array still used by native middleware.

Keep null/missing distinct from an explicitly supplied empty PIN under existing device rules. A missing PIN produces the targeted guidance above even if a provider login is warm. No automatic PIN retry, new storage consent or extra entry dialog is added. The recording input snapshot closes after preparation finishes; recorded password results have separate ownership and are not the input PIN. Test normal setup, failed setup, queue rejection, cancellation while native work remains active and final cleanup using the existing disposable token fixture.

### Browser User-Agent reference and authentication re-entry

**Explicit requirement from the author:** requests made by the recording browser must carry the existing owned-browser User-Agent reference when passing through the configured proxy path, so Burp does not start authentication again for the login traffic itself. This requirement applies to recording as well as Test login; it is not optional recorder instrumentation.

The current `AuthTrafficGuard` issues an active lease and appends an opaque `BPSHAuth/<nonce>` suffix to the real User-Agent. `BrowserFlowRunner` both decorates the browser-context User-Agent and installs context-wide request routing to preserve/reapply that same lease marker. The shared launcher must move both responsibilities together, along with the existing native-tag rejection and request-routing failure handling. Leaving routing inside the authentication-only execution method would make the recording integration incomplete.

Acquire the authentication-traffic lease with `AuthTrafficGuard.begin()`, not `beginReplay()`, whenever the launch uses the configured upstream proxy or attempt-owned mTLS transport. Read the real browser default User-Agent through the existing bootstrap path; preserve its full contents. Set the decorated context User-Agent and install request routing before the first Login URL navigation. Reuse the same active lease for initial navigation, redirects, subresources, frame requests, popup requests and fetch/XHR throughout the recording. Preserve the existing fallback to the real browser User-Agent for routed requests whose header map omits it, including the current worker-script case. ### Recorder lifecycle and event transport

Setup includes **Allow untrusted HTTPS certificates**, off by default. It applies to this journey's Chromium context for both recording and Test login, with either a direct connection or an explicit proxy. It does not install a CA, change system trust, affect other journeys or disable the client-certificate transport's upstream verification. That transport continues to use its existing Trusted CA setting. The optional `browser.ignoreHttpsErrors` field and matching draft flag default to false when absent, including older saved drafts.

Use an explicit lifecycle: Preparing, Recording, Stopping, Review, Applying, then Closed. Preparation validates the visible setup snapshot, serializes behind admitted editor writes and starts the shared browser session on its owning worker. Pause further autosave admission through review; unfinished names, aliases, old steps and capture settings do not have to become executable or persistable to start recording. Capture the resulting current storage revision after the write barrier and recheck it before applying. Resume normal autosave on discard or replacement. Install the private event observer and page/frame lifecycle listeners and start recording on the managed context before initial navigation. Preparation and navigation errors retain the old steps and produce classified guidance.

Browser preparation has a separate 60-second budget within the recording's 30-minute overall lifetime. Display the fixed cache-wait, verification, extraction, driver-start, Chromium-start and login-navigation stages in the recording dialog. Runtime linkage failures must close the recording with safe reload guidance and release its reservation, rather than leaving the dialog waiting for a worker that has exited.

The recorder worker must continue pumping Playwright events while waiting for user activity. Use bounded Playwright event waits and a thread-safe command channel for Stop/Cancel; do not block the owning thread on a UI future or use Thread.sleep as an event pump. Only the owner calls Playwright. The driver watchdog remains able to terminate the owned process tree when cancellation cannot complete normally.

Accept recorder messages only for the owned recording context and epoch. Keep page/reference decoding, protocol access and private Java reflection in the runtime adapter, with normal responses and events preserved for the existing Playwright connection. Decode only supported structured fields into bounded application records and deliver them on the owning browser worker. Reject malformed/unexpected required shapes safely. Drop `code`, `ariaSnapshot` and ephemeral recorder refs before application retention. Protocol debug output remains disabled because it could expose credentials.

Use actionAdded to append a provisional source action, actionUpdated to replace the corresponding last upstream action, and signalAdded to associate page-scoped observations. Keep a source-action-to-candidate mapping so updates do not target an inserted frame-switch row by accident. Do not append a separate click for an upstream checkbox action or reconstruct keystrokes from a fill. The private adapter does not grant arbitrary commands to page code.

The user clicks Stop once. On its owning worker, send stopRecording while the context is still open and process the delivered actions/updates/signals through the command response before freezing the result. Apply the existing 5-second Stop budget. Known command/transport failure or overflow makes the recording incomplete. Do not introduce terminal watermarks, a replacement sealing protocol or click interception. Verify immediate submission, final edits without blur, redirects and popup closure in browser tests. An ambiguous popup action association remains review-resolvable as specified below.

Stop ends collection, resolves pending operations and closes browser resources before enabling application of the review. Cancel, timeout, unexpected initial-browser closure, journey deletion, journey switch or unload discards uncommitted candidates and owned secret buffers. Closing a recorded popup during Recording can be a captured page-close action; it does not cancel the whole session. Closing the initial page unexpectedly is distinct from an intentional recorded page-close transition. No background authentication cancellation may be triggered merely to discard a recording.

### Critical user journeys and acceptance requirements

* **New login:** Given Setup is valid and capture rules are unfinished, when the user records a username/password login and applies it, then the steps and recorded password are available for editing/testing without re-entry. Password persistence still follows Remember secrets.
* **Federated login:** Given a login uses a cross-origin nested frame and an opener-owned popup, when recorded, reviewed, applied and tested, then explicit context steps select the intended frames/pages and return to the opener. A delayed popup after more than one possible opening action requires review selection. Replay uses the reviewed opener/action relationship and rejects competing popup matches; opener identity alone does not prove action causality.
* **Form controls:** Given checkbox/radio state, single/multiple select and Enter submission, when recorded and replayed from a fresh context, then the desired states and submission behavior are preserved without duplicate interactions.
* **Discard and stale completion:** Given an existing sequence, when recording is cancelled, times out, loses its initial browser or becomes stale, then the old steps remain and uncommitted secrets are released. No late completion mutates another journey.
* **Replacement and Undo:** Given existing steps with secrets, when a replacement is applied and then undone, then the original UUIDs, order and secret associations return within the current bounded undo lifetime.
* **Secret boundary:** Given the user types a password, clicks Show password and edits the visible value, when the recording is applied with Remember secrets off and exported with Include secrets off, then both fills remain secret-backed and the password is absent from ordinary configuration and export text. Ordinary fields remain ordinary under the selected policy, and no entered values appear in summaries or logs.
* **Lifecycle:** Given proxy/mTLS setup or any later recording phase fails, when cleanup completes, then owned browser, context, driver and transport resources are released. Actual platform/device observations remain separate from unit assertions.
* **Compatibility:** Given an old saved/exported journey, when loaded and tested, then behavior remains unchanged. New operations round-trip through project/user storage, import/export and unfinished drafts with correctly remapped identities.
* **Recording completion:** Given rapid submission, redirects and popup closure, when the user clicks Stop recording, then browser tests must show the expected ordered actions and final values in the result. Collect final edits from still-open pages/frames and process queued events before review. Known delivery failures, message gaps, forged messages, unsupported targets and overflow mark the result incomplete. Captured rows remain replaceable when present, within the existing resource bounds; the absence of a terminal acknowledgment from an old page does not make a recording incomplete.

Reuse authentication-lab/federation fixtures and isolated production acceptance overlays. Verify architecture, focused codec/editor/runtime regressions and existing authentication setup/cancellation tests after extracting the launcher. Implementation evidence is tracked by phase below; design probes do not replace product qualification.

## Alternatives Considered

The author selected the private Playwright recorder, full form/frame/popup support, password-type classification, replacement after review, explicit context-switch steps and a shared browser launcher. The alternatives below describe the trade-offs of the selected approach.

### Build a custom collector on public Playwright APIs

Inject a DOM event collector through public initialization-script/binding APIs and implement selectors, control-event handling, action coalescing and navigation collection in this project. This avoids private recorder API compatibility but makes the extension maintain general recording semantics. Not selected for the revised architecture: the existing driver already supplies structured recording events, and a Java transport probe demonstrated access without TypeScript or a driver fork. Use a custom collector only after a new author decision if private integration proves unsuitable.

### Chrome DevTools Recorder

Record in DevTools and import JSON, or build another bridge to its recorder implementation. This is suitable for an explicit external-recording/import feature, but its documented extension points center on export/replay rather than our native Java-controlled Record/Stop flow. It adds another workflow/integration and storage surface. The author selected reuse of the recorder already inside the managed Playwright runtime.

### Convert generated Playwright source

Run Codegen and parse generated statements. This adds source formatting/locator translation compatibility and potential plaintext password outputs without a benefit over the observed structured driver event route. Consume action objects instead; do not parse or execute generated code.

### Limit recording to the current step types or one page

A click/fill recorder could retain the current action model; a one-page form recorder could add controls without handling frames and popups. These reduce the initial model and replay changes. They cannot represent the frame/popup login flows included in the author's selected scope. Not selected by the author, who chose form controls, frames and popups for the first delivery. The wider scope therefore needs corresponding implementation and acceptance coverage, not a later unsupported-action shortcut.

### Treat every fill as secret or require classification review

Keeping all fills secret protects sensitive fields that have no password semantics, but changes harmless text into secret-backed steps. Heuristic classification followed by mandatory review reduces that effect but adds review work and still cannot reliably recognize arbitrary sensitive fields. Not selected: the author specified HTML password input types as the automatic classification rule and asked to retain the captured values without re-entry. The consequence is explicit: custom sensitive text inputs remain ordinary unless the user changes their step type. The later author-selected fallback applies only to unknown classification: those fills default to Enter secret with a nonblocking warning and can be corrected manually.

### Record fields without retaining their values

Collect field targets and actions while leaving values missing for the user to enter in Burp. This reduces copied credential material but repeats user work and prevents immediate replay. Rejected by author: users should not have to enter the same input twice. The selected collector therefore retains ordinary values and separately owned password values under the existing persistence consent rules.

### Append or offer both Replace and Continue

Replay the saved prefix before recording a continuation, then append its actions. Offering both modes serves partial journeys as well as replacements. It requires an executable prefix, secret availability, prefix-failure handling and a policy for authentication's early credential completion. Not selected by the author, who chose replacement from a fresh context. Existing steps remain intact until the replacement is applied; continuation is outside this feature.

### Put page/frame targets on every action

Store a page reference and frame path on each action, with explicit popup creation relationships. This keeps an action attached to its target when reordered and avoids ambient context. It repeats target metadata and adds target fields to ordinary rows. Not selected by the author, who chose explicit context-switch steps. The chosen design must therefore validate transitions and make the consequences of moving/removing switches visible.

### Keep recorder browser setup separate

Build a separate recorder launch path over existing runtime, driver, proxy and certificate services. This avoids extracting the authentication runner's setup, but duplicates orchestration. In particular, User-Agent marker decoration without the accompanying context request routing would leave recording exposed to authentication re-entry. Not selected by the author, who chose a shared launcher. Regression checks must verify that the extraction preserves authentication setup, traffic ownership and cleanup behavior.

### Popup opening-action association

Use Playwright's actual opener page to establish page ownership. Do not infer ownership from browser focus, page-list positions or URLs. Record popup creation and closure even when no action has yet been assigned.

For an automatic suggestion, consider supported recorded click/Press key actions on that opener after its latest document navigation or previously observed popup creation, whichever occurred later, and before the new popup creation. Exactly one candidate produces a preselected suggestion. Zero candidates leaves the relationship unassigned; more than one requires an explicit choice. These are review suggestions based on observed order, not a claim that Playwright proves action causality. Do not silently choose the most recent click. If ordering is uncertain, leave the suggestion empty.

The review allows choosing an earlier recorded click/Press key action on the same opener before the popup's first recorded use, including an earlier action outside the suggestion window for delayed popups. Show step number and action label; retain the source step UUID. Prevent assigning one action to multiple popup declarations or creating a forward/cyclic page dependency. If there is no representable earlier action or no reliable opener, the unresolved rows may be replaced as a draft and repaired manually; they cannot execute until validation succeeds. Selecting an opening step resolves only the association; it cannot dismiss an observed lost event or unsupported interaction.

Insert the expectation immediately before the chosen trigger after any required frame switches, and associate the resulting popup with the opener page regardless of which child frame contained the triggering element. On replay, install listeners before navigation, arm the declaration before the trigger and allow later opener actions while one popup is pending. Expire using the existing browser-action timeout from trigger execution, capped by the attempt deadline. Switching to the pending page waits only for the remaining budget. A popup that closes before its first required use produces an attributed closed-page failure, not a fallback to another page. Multiple competing popup creations from one opener fail instead of being selected by arrival order.

Acceptance cases must cover: one click followed by one popup (suggest the click); delayed popup after clicks A then B (require a choice, permit A); zero recorded trigger candidates (leave unassigned); two candidate triggers for one opener (no automatic latest-click choice); multiple popup matches during replay (fail); wrong opener (no match); and popup closure before first use (closed-page failure). A single unrelated script-created popup is not distinguishable from the intended popup by opener/event order alone. State this limit and rely on explicit review plus fresh-context Test login, rather than claim unsupported causal certainty.

### Exact selector boundaries and source-frame association

Use the pinned driver's `packages/isomorphic/selectorParser.ts` lexical rules as the compatibility reference. BrowserTargets owns a small Java tokenizer, not a CSS parser or a selector generator. A selector is a chain of engine components separated by an unquoted, unescaped `>>`. Track single, double and backtick quotes and backslash escapes. Preserve the pinned legacy `text=` quote exception: a quote after existing unquoted text does not start a quoted region. Trim only component-boundary whitespace; preserve body bytes. Explicit engine prefixes match `[a-zA-Z_0-9-+:*]+` before the first `=`; otherwise use pinned text/XPath/CSS inference. Reject empty components, unclosed quotes, dangling escapes and capture-engine prefixes such as `*css=`. CSS's ordinary universal selector `*` is not an engine capture.

For recorded components accept CSS/css:light, XPath, id, text, nth, visible, internal:role, internal:text, internal:label, internal:attr, internal:testid, internal:has-text and internal:has-not-text. Accept nested internal:has, internal:has-not, internal:and, internal:or and internal:chain only with one JSON string body; decode and validate recursively without changing its stored source. A nested selector cannot be first and cannot contain a frame control. Reject spatial-distance operators, unknown engines, malformed nested JSON, nested frame controls and custom engines. CSS/role body semantics remain the pinned runtime's responsibility at replay; lexical acceptance is not proof that a target exists. Apply the 4,096-byte selector bound, 256 total components including nested bodies and 16 levels of nested-selector recursion. These recorder-conversion restrictions do not rewrite or narrow legacy manually saved selectors.

Recognize frame transitions only when an entire top-level component has name internal:control and exact body enter-frame. Split into nonempty per-frame chunks, preserving the leaf chain. Reject leading, trailing or consecutive enter-frame markers and unknown controls. Quoted or nested occurrences are not outer transitions. A leading internal:control=any-frame is native shorthand, not explicit ancestry; resolve it through the actual source frame below, never persist it as a broad frame search.

**Why source metadata is required:** the bundled recorder's buildFullSelectorForFrame can replace a nested path with any-frame when it currently resolves uniquely. A Windows probe actually received `internal:control=any-frame >> internal:role=button[name="Nested target"i]` for a click two frames deep. The earlier assumption that every recorded selector carries all ancestors is false. Preserve explicit frame steps using browser-owned source identity, without changing the driver or parsing generated code.

Before recording starts, expose one bounded metadata binding in the managed context and install the metadata wrapper. For each native interaction call, create a per-document source-action key, annotate the action as bpshSourceActionId and send that key only through the metadata binding. Forward the original recorder call immediately in the same invocation; never wait for the metadata acknowledgment before forwarding. The browser gesture is not intercepted or delayed. Awaiting that acknowledgment caused a final-fill omission in an isolated candidate and is not the selected mechanism. Observe binding rejection through bounded internal failure state, without logging values or raw page errors.

The Java callback uses BindingCallback.Source.context/page/frame to establish ownership, checks the active recording context, records that actual source Frame against the key and returns promptly. A page-supplied key, frame ID, URL or document ID cannot establish frame ownership. Correlate the native action with that callback by key; allow either arrival order in a bounded worker-owned pending map. Keep Page/Frame handles inside the browser package. Missing, conflicting, wrong-context or expired source associations never become guessed targets. A complete native path may still supply explicit ancestry; unresolved any-frame prevents Apply with affected-action guidance. This target-ownership failure is distinct from the author's nonblocking password-classification warning.

For any-frame, walk the actual source Frame.parentFrame chain to the page main frame. Obtain each child's frameElement handle and ask its parent frame's pinned `window.playwright.selector(element)` helper for the native owner-element selector. Dispose temporary ElementHandles in finally. This reuses Playwright's generator instead of building CSS paths. Parse each owner selector through the same supported grammar; it must select one immediate child frame and contain no frame-control token. Use the original native leaf chunk unchanged; replace the any-frame shorthand and its shortened ancestry with this actual complete path. If a frame/owner detaches, the helper is absent, or an owner selector is unsupported/ambiguous, report an unresolved target; never choose another frame by URL, text search or focus. Compilation receives immutable path strings and logical page identity, not handles.

Use the longest exact common prefix of the previous/current explicit path on the selected logical page: emit Leave frame until that prefix, Enter frame for the remaining owner selectors, then the action with its leaf selector. Switch page resets the prior frame path. If the previously selected actual frame has detached, emit Leave all frames and re-enter the current complete path instead of walking a stale frame handle. Closing a page needs no frame transition. Textually different paths may cause extra transitions but must not be assumed equivalent. Count inserted transitions toward the 256-step cap. An empty path targets the selected page outside frames.

The adapter assigns a provisional action ID on actionAdded; the pinned action object has no stable source ID. On actionUpdated, verify that the immediately preceding native action is a fill with matching page and native selector, following the pinned app's merge rule. Replace that provisional candidate and retain its logical ID; the new bpshSourceActionId resolves updated metadata, not a new saved step UUID. Never update an arbitrary selected UI row. If the actual frame/document/field identity differs, preserve the earlier candidate and start a distinct fill instead of merging different targets. Signals retain page-scoped association and the existing popup review rule.

Bound outstanding source keys with the same 256-event queue and 4 MiB candidate limits, at most 128 ASCII bytes per key. Consume associations after normalization. Metadata for an upstream-superseded action may remain unmatched; discard unused entries after successful upstream Stop/flush, not as proof of a lost action. A referenced action missing required target metadata remains unresolved. Process callbacks within the existing five-second Stop budget; do not add a document seal or network request. Release pending handles/maps on Stop, Cancel, timeout and unload. Helper evaluation and selector generation run on the recording worker within deadline/cancellation ownership.

Required fixtures cover quoted `>>` in CSS/role names, escaped quotes, nested JSON, legacy text apostrophes, compound selectors on each side of a boundary, two frame transitions, unknown controls, any-frame without source identity, captures, malformed nesting and depth/size limits. The isolated tokenizer matched the pinned lexer on ten cases and rejected seven invalid/unsupported forms (`selector-lowering-probe.json`). A Windows candidate associated the actual source frame through the binding, generated both native parent selectors and replayed the leaf on the same two-frame target (`frame-source-bridge-probe.json`); it also retained final fills and password/replacement classifications. These are limited proofs, not production acceptance. Qualify the actual Java helper, duplicate leaves in different frames, nested cross-origin frames, rapid navigation/closure, update merging, callback reordering/failure, cancellation, bounds and supported platforms in the shared lab.

On a normal editor action-type change, retain row UUID and selector only if both old/new operations use an element or frame selector. Clear old operation-specific fields, create the new operation's defaults and preserve the existing ordinary/secret value-clearing rules. Changing Enter secret to ordinary input in the normal editor clears the value. Switching operations must not preserve a hidden previous popup reference or option list. Structural Undo retains the old row and its owned secret association through the existing bounded session-only mechanism.

Recording review has an explicit exception for changing Fill field and Enter secret. On the user's deliberate Enter secret to Fill field choice, transfer the captured value from the review secret snapshot into ordinary candidate text, preserve missing versus explicitly empty, remove and wipe the released owned secret buffer, and clear the classification warning for that corrected row. On Fill field to Enter secret, copy candidate text into a separately owned secret buffer and remove the ordinary candidate value; do not imply that immutable transient strings can be wiped. Changing to an unrelated action retains the normal clearing behavior. These are review-only candidate changes and trigger no autosave before Apply. Apply passes the candidate values through the existing replacement boundary once, with the selected type and normal Remember secrets rules. Cancel closes the current candidate snapshot. Undo after Apply restores the previous journey sequence and its owned secrets; it never restores the discarded recording as a second saved copy. Tests must assert exact value preservation through both review type conversions, no pre-Apply persistence, missing/empty handling, Apply, Cancel and replacement Undo. No second value entry is required.

For imports/copies, allocate all destination step UUIDs before remapping references. A valid draft `triggerStepId` matching a source row becomes that row's destination UUID. Empty, malformed and syntactically valid-but-unresolved references remain literal invalid draft text for correction; they must not be rebound to an unrelated destination row. Page names remain local to the copied journey. Apply the same two-pass mapping to executable references and secret associations. Do not silently compile a draft just to copy it.

`structuralSteps()` remains an ownership/identity view, never an executable compilation route. Preserve every row's UUID and kind, with a type-compatible placeholder payload where its raw fields cannot be represented as executable values; use false/empty-list/Enter/empty-page and the row's own UUID as the respective placeholder defaults. Raw fields remain authoritative in the draft and are not replaced by those placeholders. All runtime entry points must continue rejecting definitions carrying a non-null draft. Transfer maps IDs from the original draft rows, not from placeholder reference values. Add tests proving invalid draft references cannot become executable or silently valid after import.

Add two explicit fixture files: a legacy step-draft inventory with no `operation` fields, and a new step-draft inventory covering every new operation. Use fixed fake UUIDs and no passwords. ### Verification and delivery

Use deterministic unit fixtures for transformation/ownership behavior and the installed Burp Browser for event transport, navigation and replay. Tests must assert actual values/state and protected identity, not only that a callback ran. Keep fixture passwords local to tests; no production credentials enter evidence. No percentage coverage target substitutes for the cases below.

| Scope | Required observed outcome |
| --- | --- |
| Version-1 codec/compiler | Old journeys remain executable; all new operations/drafts round-trip; wrong fields and broken references fail with indexed guidance; import remaps triggers and secrets together. |
| Input transport | Typing, paste, composition, supported autofill, show-password toggles, immediate submit/navigation and Stop preserve final observed values or refuse Apply for a detected delivery failure. Unknown password classification instead retains a masked Enter secret value and shows a nonblocking warning. Verify no-password-detected guidance, manual type changes, sticky known-secret status and no ordinary persistence before explicit correction. No second password entry is required. |
| Replay | Fresh-context checkbox/radio state, option selections, Enter submission, nested cross-origin frames, delayed popup and opener return match the performed login. A detached or ambiguous target never falls back. |
| Ownership and UI | Cancel, timeout, unload, stale editor revisions, external reload, replacement/Undo and failed autosave retain the specified step/secret ownership; UI stays responsive. |
| Action-picker help | Every existing/new selectable operation shows its own concise tooltip on hover before selection in add, row and review pickers. Keyboard/accessibility help matches. Hover never selects, adds or saves; native Burp checks cover actual popup behavior, scaling and screen edges. |
| Recursion prevention | With automatic scopes matching login/identity-provider traffic, actual request/response hooks cause zero nested acquisitions, injections or recovery. Destination sees original User-Agent; popup/frame/fetch/worker paths and revoked markers have explicit results. |
| Shared launcher regression | Authentication deadlines, response-only early completion, required cookie-login steps, retries, PKCS#11/proxy behavior and context/driver/transport cleanup follow the current authentication contract. |
| Limits | Recording caps, detected message gaps, observed delivery failures, failed Stop-time collection and ambiguous popups result in bounded failure/incompleteness. A page navigating away does not require a terminal acknowledgment. Exact-sequence browser tests guard against silently lost actions; they have not yet run. |

Run these commands from the repository root. Use `.\bapp\gradlew.bat -p bapp check verifyNativeDocumentation --offline` for native regressions and architecture, and `.\bapp\gradlew.bat -p bapp browserIntegrationTest --offline` for bundled-browser behavior through the existing owner. Run `.\bapp\gradlew.bat -p bapp pkcs11IntegrationTest --offline` only with a fresh explicit disposable fixture under the existing documented prerequisites. After intentional harness/catalog changes, invoke `.\bapp\gradlew.bat -p bapp :auth-lab:refreshBindings --offline`, review its complete diff, then run scoped browser/federation/Burp acceptance in a separate invocation following the lab README. Source binding refresh is not a passing test.

Build the verified universal artifact directly to `bapp/build/libs/browser-powered-session-handler-dev.jar` using the maintained build task. Verify the selected driver package/version and Windows x64/Linux x64/Intel macOS resources are present; the private Java adapter uses the unchanged bundled driver. Before replacing the active-worktree JAR in Burp, toggle the existing extension's Loaded checkbox off, replace it, then toggle it on; do not remove/re-add it. Actual Burp checks must qualify the User-Agent re-entry path, native recording/review controls and cleanup. Bundled resources do not establish execution on every platform or physical-device compatibility.

The recording implementation and its acceptance scope are separate. Full-feature acceptance still requires the platform, provider and host checks specified by the lab; native unit checks and controlled Windows browser scenarios do not establish those observations.
